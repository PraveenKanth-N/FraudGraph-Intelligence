Frequently Asked Architectural Questions

How does FraudGraph differ from standard Neo4j or TigerGraph clusters? expand_more

Standard graph databases run primarily on general-purpose CPU architectures and rely on disk or distributed JVM RAM caching. While suitable for analytical queries, they incur substantial latency (often 80ms to 800ms) during multi-hop cycle searches.

FraudGraph operates strictly in GPU High-Bandwidth Memory (HBM3) using custom CUDA FP8 kernels. We execute massive graph isomorphism searches in parallel across thousands of tensor cores, maintaining deterministic latencies below 1 millisecond.

What hardware topology is required to achieve sub-millisecond traversal? expand_more

Our reference cluster leverages NVIDIA HGX H100 or H200 8-GPU systems interconnected with 900 GB/s NVLink fabrics. Network ingestion uses dual 400Gb/s ConnectX-7 NICs supporting RoCE (RDMA over Converged Ethernet) to stream incoming banking events directly into GPU memory with zero host CPU intervention.

How are zero-knowledge audit proofs generated without exposing consumer PII? expand_more

FraudGraph hashes incoming account identifiers and attributes locally at the perimeter. Detection logic operates entirely on numerical node features and topological properties. When an alert triggers an automated settlement halt, the engine compiles a succinct zk-SNARK cryptographic receipt proving topological cyclicity without revealing names, balances, or raw IBAN numbers.

Can the CUDA graph engine integrate with existing Kafka event streams? expand_more

Yes. FraudGraph ships with high-throughput native Apache Kafka and Redpanda connectors utilizing our zero-copy librdkafka C++ bridge. Inbound event batches are pinned directly to GPU memory buffers, sustaining upwards of 120,000 messages per second per appliance.
